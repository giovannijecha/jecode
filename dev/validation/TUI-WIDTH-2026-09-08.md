# Terminal width allocation investigation

This is development evidence for PR #138, not a live provider comparison or
release-candidate acceptance record. The correction changes only the width
measurement of wholly printable ASCII; it does not change model requests,
rendered content, layout, permissions, or persistence.

## Signal and diagnosis

Two hosted collections compared the original PR runtime with `768b6869`.
In the 120-column, 2,000-block, 32 KiB/s case, menu input-to-frame p95 rose
from 43.921 to 55.663 ms in the [first collection], and from 50.845 to 58.136 ms
in the [second collection]. The latter three-run ranges did not overlap.
The rendering source was unchanged at that point. Green acquisition checks
did not clear this performance observation.

A private WSL profile of `a31db27` showed approximately 1,602 ms of self time in
`textWidth`, 857 ms in `segmentGraphemes`, and 674 ms in garbage collection
across the full synthetic sequence. In a further instrumented candidate run,
the five slowest menu frames overlapped minor-GC pauses of 7.732–12.186 ms.
Those frames accepted no output; the differential painter itself took only
0.002–0.003 ms. This identified allocation pressure around frame composition,
not a slow provider request or a blocked write in those samples.

Previously every width check allocated Unicode grapheme records even for
ordinary ASCII labels, paths, code, and whitespace. The correction returns
the string length only when every code unit is in U+0020–U+007E. Controls,
combining marks, variation selectors, emoji, CJK, and malformed surrogates
retain the existing Unicode path. It adds no text cache or retained history.

This removes a measured pre-existing hotspot. It does not establish why the
transport branch originally changed the placement of GC pauses on hosted
runners, or promise to remove every long frame.

## Controlled repeat

The timing repeat used the original `dev/benchmarks/tui.ts` and its unchanged
helpers, without a CPU profiler, GC observer, or temporary frame instrumentation.
Each process ran all four scenarios in the existing order, with 25 warm-up
inputs and 100 observations per interaction phase. `NO_COLOR=1`, reduced
motion, synthetic history, and an isolated development home were used.
No provider connection, command tool, or production user-data store was used.

- Before: `a31db27dff54e83730f9e0ce4fed631c96d77ac8`.
- After: the same source snapshot with only `src/ui/width.ts` replaced by the
  correction accompanying this report. Other changed files are tests and docs.
- Runtime: Node 24.20.0; x86_64 WSL2 Linux
  `6.18.33.2-microsoft-standard-WSL2`, glibc 2.43.
- Command: `node --expose-gc dev/benchmarks/tui.ts` in each isolated snapshot.
- Six fresh processes, sequential order: before, after, after, before, before,
  after. No local test suite or second benchmark ran concurrently.
- Width-source SHA-256 before:
  `d4137b76379d6f4cf9cf4b2e73e21de5a1371270103e90e585a3095d68065476`.
- Width-source SHA-256 after:
  `ef7d8d7770550630c12335650892270974494947905c01c7aa097f429229ff80`.

Values below are the median of three per-run input-to-frame p95 measurements,
in milliseconds. Brackets show the minimum and maximum across those runs.

| Menu scenario | Before | After | Change |
| --- | ---: | ---: | ---: |
| 120 columns, empty history | 20.393 [20.325, 20.594] | 18.600 [18.433, 18.601] | -8.8% |
| 120 columns, 2,000 blocks | 20.172 [20.084, 20.210] | 18.382 [18.196, 18.640] | -8.9% |
| 60 columns, 2,000 blocks | 20.120 [20.117, 20.177] | 18.463 [18.447, 18.630] | -8.2% |
| 120 columns, 2,000 blocks, 32 KiB/s sink | 23.805 [23.774, 23.970] | 18.329 [18.169, 18.453] | -23.0% |

All four menu ranges are separated. In the slow-output case, typing during
streaming changed from 19.036 to 17.920 ms (-5.9%), and resizing during streaming
from 33.354 to 18.681 ms (-44.0%). Idle typing stayed near the frame-timer floor:
17.385 to 17.476 ms in that case; changes across all four idle cases were
+0.010–0.137 ms. This is not an improvement claim for every individual metric.

## Verification and limits

- A regression test first failed on the old implementation because printable
  ASCII still requested grapheme segmentation, then passed with the correction.
- Explicit tests cover all ASCII controls at the beginning, middle, and end;
  CRLF; combining marks; emoji selectors and ZWJ sequences; flags; fullwidth
  and supplementary CJK; and malformed UTF-16.
- The focused UI, menu, colour, and benchmark suite passed all 44 tests.
- Windows / Node 24.18.0 `npm run check` passed: 1,091 tests, 1,080 passed,
  11 platform skips, zero failures. Coverage: 96.23% lines, 89.02% branches,
  94.28% functions. Package: 192 files, 1,930,141 unpacked bytes, no runtime
  dependencies; installed CLI version remains 0.8.7.
- Exact-head hosted CI and benchmark links belong in the PR validation record,
  so later runs do not rewrite this local experiment's provenance.

Three runs per variant remain a small synthetic sample. These measurements
show less rendering work in this workload, not physical key-to-display latency,
faster model generation, or higher task quality than another coding agent.
The existing probes keep their workloads and thresholds. Real-terminal,
screen-reader, all-provider, and prolonged-use validation remain required.
